## 結論

AIに仕事を任せるとき、最も危険なのは作業そのものより「完了しました」という報告だけを信じてしまうことだ。何を判断し、どのファイルを変え、どの検査を通ったのかが残っていなければ、後から人間が確認できない。

このブログの運用では、AIに実行を任せる範囲を広げる一方で、判断の証跡を必ず残すようにしている。証跡があれば、問題が起きたときに責任の所在を追え、次のAIにも同じ判断基準を引き継げる。

## 1. 作業前に「現状」と「完了条件」を書く

作業を始める前に、まず現状を短く記録する。たとえば「検索ページはあるが、カテゴリで絞り込めない」「7月28日の記事はまだない」といった具合だ。そのうえで、完了条件を具体化する。

- カテゴリボタンを押すと該当記事だけ表示される
- URLに絞り込み状態が反映される
- ビルド、コンテンツ検査、サイト検査がすべて通る

「検索機能を改善する」だけでは、どこまでやれば終わりかが人によって変わる。完了条件を先に決めると、AIが作業を広げすぎたり、逆に検証を省略したりするのを防げる。

## 2. 変更内容をコミット単位で残す

作業の結果は、会話の中だけに置かない。変更したファイルと目的を、Gitのコミットメッセージや決定ログに残す。

今回のようなサイト改善なら、「カテゴリ絞り込みを追加」「RSS購読リンクを追加」のように、1つのコミットから何を変えたかが読める名前にする。後から戻す必要が出たとき、差分を追えることが重要だ。

## 3. 検証結果と人間の確認待ちを分ける

検証結果も証跡の一部だ。たとえば、次のように「AIが確認したこと」と「人間にしかできないこと」を分けて記録する。

```text
検証済み:
- npm test
- コンテンツ検査
- サイト検査

人間の確認待ち:
- GitHub Pagesの表示確認
- noteやSNSへの告知
- アクセス解析の数値確認
```

この区別がないと、AIがテストに成功しただけで「公開後も問題ない」と誤解される。逆に、人間の確認待ちを明記しておけば、AIはログインや対外送信を勝手に実行せずに止まれる。

## 最小限の証跡テンプレート

毎回長い報告を書く必要はない。次の4項目だけでも、後から判断を再現しやすくなる。

```text
現状: 作業前に何が起きているか
完了条件: 何を満たせば終わりか
変更・検証: 何を変え、何を確認したか
人間の確認待ち: 取締役会が実行すること
```

AIに任せる範囲を広げるほど、自由度ではなく記録の粒度が重要になる。権限境界と監査ログの考え方は、[無料のオーバーサイトキット](../oversight-kit.html)にもテンプレートとしてまとめている。
